TypeScript is the primary language for all frontend development at Nexium Media. Beyond basic autocomplete, TypeScript serves as executable documentation and the first line of defense against production bugs. By eliminating whole classes of runtime errors—such as undefined property access, unhandled null values, and state contract mismatches—TypeScript enables 100+ engineers to refactor codebases safely.

This guide details our strict compiler configurations, advanced type patterns, runtime schema validation with Zod, and typed React paradigms.

## Why Strict TypeScript Matters

In large enterprise applications, the cost of an uncaught runtime exception compounds across user-facing sessions, analytics reporting, and backend synchronization.

- **Compile-Time Verification**: Catches invalid payloads, missing props, and null references prior to code review.
- **Living Architecture**: Interfaces and types act as immutable contracts between frontend components and backend API endpoints.
- **Fearless Refactoring**: Global type renaming and structural updates automatically flag every affected downstream call site.

## Strict Compiler Flags Explained

Nexium Media mandates the following compiler flags in `tsconfig.json`:

| Flag | Behavior When Enabled | Why Nexium Enforces It |
| :--- | :--- | :--- |
| `strict: true` | Activates all strict type checking flags (`noImplicitAny`, `strictNullChecks`, etc.). | Eliminates implicit `any` fallbacks and ensures `null`/`undefined` are distinct domain types. |
| `noUncheckedIndexedAccess` | Appends `undefined` to index access lookups: `records[key]` becomes `T \| undefined`. | Prevents assuming an arbitrary array index or object key exists at runtime. |
| `exactOptionalPropertyTypes` | Distinguishes between omitting a key vs. providing `{ key: undefined }`. | Prevents subtle payload bugs when serializing JSON objects to external APIs. |
| `noImplicitOverride` | Enforces `override` keyword when subclassing or extending methods. | Prevents silent method shadowing when parent class contracts change. |

## `type` vs. `interface`: When to Use Each

Nexium Media follows standard conventions for choosing between `interface` and `type`:

```typescript
// Use `interface` for public API contracts, polymorphic objects, and extensible library props
export interface UserProfile {
  id: string;
  name: string;
  email: string;
}

// Interfaces support declaration merging
export interface UserProfile {
  avatarUrl?: string;
}

// Use `type` for unions, intersections, primitives, tuples, and mapped types
export type UserRole = "admin" | "editor" | "viewer";
export type Coordinates = [latitude: number, longitude: number];
export type Nullable<T> = T | null;

// Intersection with type
export type AuthenticatedUser = UserProfile & {
  token: string;
  role: UserRole;
};
```

<Callout type="tip">
Prefer `interface` for React component props and standard domain models to take advantage of superior compiler diagnostic performance. Use `type` aliases for complex unions, mapped types, or utility transformations.
</Callout>

## Discriminated Unions for State Machines

Boolean flags like `isLoading`, `isError`, and `isSuccess` often lead to impossible states (e.g., both `isLoading` and `isError` true). We mandate **discriminated unions** with a single discriminant literal tag:

```typescript
// Anti-Pattern: Boolean flags permit impossible states
interface BrokenState {
  isLoading: boolean;
  isError: boolean;
  data: UserData | null;
  error: Error | null;
}

// Best Practice: Discriminated Union
export type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

// Exhaustive Pattern Matching in React
export function renderState<T>(state: AsyncState<T>) {
  switch (state.status) {
    case "idle":
      return null;
    case "loading":
      return <LoadingSpinner />;
    case "success":
      return <DataView data={state.data} />;
    case "error":
      return <ErrorMessage message={state.error.message} />;
    default: {
      // Exhaustiveness check: compile error if a state variant is unhandled
      const _exhaustive: never = state;
      throw new Error(`Unhandled state variant: ${_exhaustive}`);
    }
  }
}
```

## Generics & API Response Wrappers

Generics allow building reusable, type-safe data pipelines without sacrificing type precision:

```typescript
// Standard Nexium REST API Envelope
export interface ApiResponse<TData, TMeta = Record<string, unknown>> {
  data: TData;
  meta: TMeta;
  timestamp: string;
  status: "ok" | "error";
}

// Generic Paginated Metadata
export interface PaginationMeta {
  page: number;
  pageSize: number;
  totalCount: number;
  hasNextPage: boolean;
}

export type PaginatedResponse<TItem> = ApiResponse<TItem[], PaginationMeta>;

// Generic API Client Fetcher
export async function fetchJson<TResponse>(url: string): Promise<TResponse> {
  const res = await fetch(url);
  if (!res.ok) {
    throw new Error(`HTTP Error ${res.status}: ${res.statusText}`);
  }
  return (await res.json()) as TResponse;
}
```

## Essential Utility Types

TypeScript provides powerful built-in utility types:

```typescript
interface Campaign {
  id: string;
  name: string;
  budget: number;
  startDate: string;
  endDate: string;
}

// Partial: Makes all properties optional
type UpdateCampaignDto = Partial<Campaign>;

// Required: Makes all properties required
type StrictlyDefinedCampaign = Required<Campaign>;

// Pick: Selects a subset of properties
type CampaignHeaderInfo = Pick<Campaign, "id" | "name">;

// Omit: Omits specified properties
type NewCampaignPayload = Omit<Campaign, "id">;

// Record: Key-value dictionary
type CampaignLookup = Record<string, Campaign>;

// ReturnType & Parameters: Extracts signature metadata
function createCampaign(name: string, budget: number) {
  return { id: "c-123", name, budget };
}

type CreateFnReturn = ReturnType<typeof createCampaign>; // { id: string, name: string, budget: number }
type CreateFnParams = Parameters<typeof createCampaign>; // [name: string, budget: number]
```

## Type Narrowing & Custom Type Guards

```typescript
interface Cat {
  kind: "cat";
  meow: () => void;
}

interface Dog {
  kind: "dog";
  bark: () => void;
}

type Pet = Cat | Dog;

// Custom Type Guard with 'is' predicate
export function isCat(pet: Pet): pet is Cat {
  return pet.kind === "cat" && typeof (pet as Cat).meow === "function";
}

// Narrowing unknown error in catch blocks
export function normalizeError(err: unknown): Error {
  if (err instanceof Error) {
    return err;
  }
  if (typeof err === "string") {
    return new Error(err);
  }
  if (err !== null && typeof err === "object" && "message" in err) {
    return new Error(String(err.message));
  }
  return new Error("An unknown error occurred.");
}
```

<Callout type="warning">
Never catch errors as `(error: any)`. In strict TypeScript, catch variables are typed as `unknown`. Use the `normalizeError` guard shown above to safely inspect exceptions.
</Callout>

## `unknown` vs. `any`: Never Use `any`

- **`any`**: Disables the type checker entirely. Any operation, method call, or property access is permitted, silently propagating runtime crashes. **Banned in Nexium codebases.**
- **`unknown`**: Represents a value of any type, but forces explicit type narrowing before any operation can be executed.

```typescript
// BANNED: Silent bug at runtime
function unsafeParse(json: string): any {
  return JSON.parse(json);
}
const result = unsafeParse("{}");
result.nonExistentMethod(); // Compiles fine, crashes in production!

// APPROVED: Forces compiler check
function safeParse(json: string): unknown {
  return JSON.parse(json);
}
const safeResult = safeParse("{}");
// safeResult.nonExistentMethod(); // Compiler Error: Object is of type 'unknown'
```

## Runtime Validation with Zod

TypeScript types disappear at runtime. When receiving data from external APIs, webhooks, or local storage, use **Zod** to validate structures at the network boundary:

```typescript
import { z } from "zod";

// 1. Define Zod schema
export const UserSchema = z.object({
  id: z.string().uuid(),
  email: z.string().email(),
  name: z.string().min(2),
  role: z.enum(["admin", "member", "guest"]),
  createdAt: z.string().datetime(),
});

// 2. Infer static TypeScript type from schema
export type User = z.infer<typeof UserSchema>;

// 3. Validate runtime payloads
export async function fetchUserById(userId: string): Promise<User> {
  const response = await fetch(`/api/users/${userId}`);
  const payload: unknown = await response.json();

  // safeParse returns a discriminated result
  const parseResult = UserSchema.safeParse(payload);

  if (!parseResult.success) {
    console.error("Payload validation failed:", parseResult.error.format());
    throw new Error("Received malformed user data from API endpoint.");
  }

  // parseResult.data is strictly typed as User
  return parseResult.data;
}
```

## TypeScript with React Patterns

```tsx
import React, { useState, useRef, createContext, useContext } from "react";

// 1. Typing Component Props
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: "primary" | "secondary" | "destructive";
  isLoading?: boolean;
}

export const Button = React.forwardRef<HTMLButtonElement, ButtonProps>(
  ({ variant = "primary", isLoading, children, disabled, ...rest }, ref) => {
    return (
      <button ref={ref} disabled={disabled || isLoading} {...rest}>
        {isLoading ? <span>Loading...</span> : children}
      </button>
    );
  }
);
Button.displayName = "Button";

// 2. Typing Event Handlers
export function SearchInput() {
  const [value, setValue] = useState("");

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    setValue(e.target.value);
  };

  const handleKeyDown = (e: React.KeyboardEvent<HTMLInputElement>) => {
    if (e.key === "Enter") {
      console.log("Submitting:", value);
    }
  };

  return <input type="text" value={value} onChange={handleChange} onKeyDown={handleKeyDown} />;
}

// 3. Typing Context
interface ThemeContextValue {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);

export function useTheme(): ThemeContextValue {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error("useTheme must be used within a ThemeProvider.");
  }
  return context;
}
```
